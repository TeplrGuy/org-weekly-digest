## The Problem

Engineering leaders managing many repositories face a common challenge:
- Activity is scattered across 40+ repos — no single view of what happened this week
- Manual status gathering takes hours and is always outdated by the time it's compiled
- Existing dashboard tools require infrastructure, maintenance, and licensing

**What the customer asked:** _"Can we have an org-level agentic workflow that will report on all 40 projects in one place?"_

## The Solution

A **single GitHub Agentic Workflow** in a dedicated reporting repo that:

1. Runs on a weekly schedule (or on-demand)
2. Uses an AI agent (GitHub Copilot, Claude, or Codex) running in GitHub Actions
3. Queries the GitHub API across **all** repositories in the org/account
4. Produces a consolidated digest and posts it as a GitHub Issue — auto-closing older digests

**No custom servers. No external infrastructure. Just a markdown file and GitHub.**

### Security Pipeline (Built into gh-aw)

Every agentic workflow run passes through a three-stage security pipeline:

```
  ┌────────┐     ┌───────────┐     ┌──────────────┐
  │ Agent  │ ──► │ Threat    │ ──► │ Safe Outputs │
  │ runs   │     │ Detection │     │ (validated   │
  │ in     │     │ scans     │     │  writes)     │
  │sandbox │     │ output    │     │              │
  └────────┘     └───────────┘     └──────────────┘

  - Sandboxed container         - AI reviews agent        - Only pre-approved
    with network isolation        output for threats        GitHub operations
  - Read-only permissions       - Blocks prompt            (create-issue, etc.)
    by default                    injection attempts      - Field-level validation
  - Tool allowlisting                                       & sanitization
```

## How GitHub Agentic Workflows Work

### Key Concepts

| Concept | What It Is |
|---------|-----------|
| **Workflow file** (`.md`) | A markdown file where you describe what the agent should do in natural language. Includes YAML frontmatter for configuration (schedule, permissions, tools, safe-outputs). |
| **Lock file** (`.lock.yml`) | Auto-generated GitHub Actions YAML that `gh aw compile` produces. This is the actual Actions workflow — you never edit it directly. |
| **Safe Outputs** | The only way an agent can write to GitHub (create issues, PRs, comments, etc.). Pre-approved operations with field validation and limits. |
| **GitHub Tools** | Read-only MCP tools that give the agent access to the GitHub API (list repos, read issues, search code, etc.). |
| **AI Engine** | The LLM that powers the agent — GitHub Copilot (default), Claude, or Codex. |
| **Threat Detection** | A second AI pass that scans the agent's output for prompt injection, harmful content, or unauthorized operations before execution. |

### Agentic Workflows vs. Traditional GitHub Actions

| Feature | Traditional Actions | Agentic Workflows |
|---------|-------------------|-------------------|
| **Configuration** | Complex YAML | Natural language markdown |
| **Logic** | Deterministic scripts, bash, code | AI agent decides dynamically based on context |
| **Adaptability** | Static — does exactly what's scripted | Adapts — handles edge cases, missing data, unexpected formats |
| **Cross-repo** | Requires custom API scripts | Built-in `tools.github` with cross-repo reading |
| **Output** | Artifacts, logs | Safe Outputs (issues, PRs, comments) with validation |
| **Security** | User-managed | Sandboxed + threat detection + safe outputs pipeline |

### Why Not Just a Script?

A traditional approach would require:
- A custom Node.js or Python script querying the GitHub API
- Pagination handling, error recovery, rate limiting logic
- Template formatting for the report
- A runner or cron job to execute it
- Maintenance as the GitHub API changes

With Agentic Workflows, you write **what you want** in markdown and the agent figures out **how** — including handling pagination, rate limits, empty repos, and formatting.

### The Workflow File Explained

The `weekly-digest.md` has two parts:

**1. YAML Frontmatter** — Configuration:
```yaml
---
description: Generate a weekly digest report aggregating activity across all repos
on:
  schedule: weekly          # Runs every Sunday
  workflow_dispatch:        # Also triggerable manually
permissions:
  contents: read            # Read code/files
  issues: read              # Read issues
  pull-requests: read       # Read PRs
tools:
  github:
    toolsets: [repos, issues, pull_requests, actions]
    github-token: ${{ secrets.GH_AW_CROSS_REPO_PAT }}  # PAT for cross-repo access
    allowed-repos:
      - "YourOrg/*"         # Which repos the agent can read
safe-outputs:
  create-issue:
    max: 1                  # Max 1 issue per run
    close-older-issues: true # Auto-close previous digests
    labels: [weekly-digest, report]
  noop:
    max: 1                  # For when there's no activity
---
```

**2. Markdown Body** — Natural language instructions telling the agent what to do, how to format the report, and what to include.

## Set It Up Yourself (Step-by-Step)

> This guide lets you replicate this workflow for **your own** org or user account.

### Prerequisites

| Requirement | How to Get It |
|-------------|--------------|
| GitHub account | [github.com](https://github.com) |
| GitHub CLI v2.0+ | [cli.github.com](https://cli.github.com/) — verify with `gh --version` |
| GitHub Copilot subscription | [github.com/features/copilot](https://github.com/features/copilot) (or an Anthropic/OpenAI key) |
| GitHub Actions enabled | Settings → Actions → General in your repo |

### Step 1 — Install the gh-aw CLI extension

```bash
gh extension install github/gh-aw
gh aw version    # Should show v0.45.2 or later
```

### Step 2 — Create a new repo for the digest

```bash
# Option A: Create from scratch
mkdir org-weekly-digest && cd org-weekly-digest
git init
gh repo create org-weekly-digest --public --source=. --remote origin --push

# Option B: Fork this repo
gh repo fork TeplrGuy/org-weekly-digest --clone
cd org-weekly-digest
```

### Step 3 — Create the workflow file

Create `.github/workflows/weekly-digest.md` and customize the frontmatter:

```yaml
---
description: Weekly digest of all org activity
on:
  schedule: weekly
  workflow_dispatch:
permissions:
  contents: read
  issues: read
  pull-requests: read
tools:
  github:
    toolsets: [repos, issues, pull_requests, actions]
    github-token: ${{ secrets.GH_AW_CROSS_REPO_PAT }}
    allowed-repos:
      - "YOUR-ORG/*"     # ← Change this to your org name
safe-outputs:
  create-issue:
    max: 1
    close-older-issues: true
    labels: [weekly-digest, report]
  noop:
    max: 1
---

# Weekly Digest Agent

Create a weekly summary of activity across all repositories in the organization.

## What to Include
- Issues opened and closed per repo
- PRs opened and merged per repo
- Commits to default branches
- Top contributors
- Trends and observations

## Format
Use tables, bullet points, and links. Group by repo.
Skip repos with no activity.
```

### Step 4 — Set up secrets

You need **two secrets**:

**Secret 1: COPILOT_GITHUB_TOKEN** — Powers the AI engine

```bash
gh aw secrets set COPILOT_GITHUB_TOKEN --value "<your-copilot-token>"
```

> To get a Copilot token, run `gh auth token` if you have Copilot access, or use an Anthropic/OpenAI key instead (see [Engine docs](https://github.github.com/gh-aw/reference/engines/)).

**Secret 2: GH_AW_CROSS_REPO_PAT** — Gives the agent read access to all repos

Create a [fine-grained PAT](https://github.com/settings/personal-access-tokens/new) with:

| Setting | Value |
|---------|-------|
| **Token name** | `org-weekly-digest-reader` |
| **Expiration** | 90 days (recommended) |
| **Repository access** | All repositories (or select specific ones) |
| **Contents** | Read-only |
| **Issues** | Read-only |
| **Pull requests** | Read-only |
| **Actions** | Read-only (optional, for workflow run data) |

```bash
gh aw secrets set GH_AW_CROSS_REPO_PAT --value "github_pat_xxxxxxxxxxxx"
```

### Step 5 — Compile, commit, and push

```bash
gh aw compile                    # Generates weekly-digest.lock.yml
git add .
git commit -m "Add multi-repo weekly digest workflow"
git push
```

### Step 6 — Trigger a test run

```bash
gh aw run weekly-digest
```

Then watch the run:
```bash
gh run watch
```

After 2-5 minutes, check the **Issues** tab — you should see a `📊 Org Weekly Digest` issue.

## Customization Guide

### Change the schedule

```yaml
# In the frontmatter of weekly-digest.md
on:
  schedule: daily          # Options: daily, weekly, monthly, or cron syntax
  workflow_dispatch:
```

### Scope to specific repos

```yaml
tools:
  github:
    allowed-repos:
      - "my-org/frontend-*"     # Only frontend repos
      - "my-org/backend-*"      # Only backend repos
      - "my-org/infra"          # Specific repo
```

### Change the AI engine

```yaml
# Use Claude instead of Copilot
engine:
  id: claude
```
Then set `ANTHROPIC_API_KEY` as a secret instead of `COPILOT_GITHUB_TOKEN`.

### Add more safe outputs

```yaml
safe-outputs:
  create-issue:
    max: 1
    close-older-issues: true
  create-discussion:         # Post as a Discussion instead
    max: 1
    category: "Announcements"
```

### After any frontmatter change, recompile

```bash
gh aw compile
git add . && git commit -m "Update workflow config" && git push
```

## Security & Permissions Model

| Layer | Protection |
|-------|-----------|
| **Sandbox** | Agent runs in a Docker container with network isolation. Only allowlisted domains are reachable. |
| **Read-only by default** | The `GITHUB_TOKEN` and agent permissions are read-only unless explicitly granted via safe outputs. |
| **Safe Outputs** | The agent cannot directly call the GitHub API to create/modify resources. It must use safe output tools which are validated, sanitized, and rate-limited. |
| **Threat Detection** | A second AI agent reviews the primary agent's output for prompt injection, data exfiltration, or unauthorized operations before any writes execute. |
| **Tool Allowlisting** | Only tools explicitly listed in the frontmatter are available to the agent. |
| **PAT Scoping** | The cross-repo PAT should be scoped to read-only permissions only on target repos. |

### Token Strategy for Enterprises

| Approach | Use Case |
|----------|---------|
| **Fine-grained PAT** | Quick setup, personal accounts, small orgs |
| **GitHub App** | Enterprise orgs — automatic token minting/revocation, audit trail, not tied to a human account |
| **Magic secret** (`GH_AW_GITHUB_MCP_SERVER_TOKEN`) | Convenience shortcut — set once, recognized by gh-aw automatically |

## FAQ

**Q: Does this work for GitHub Enterprise Cloud?**
A: Yes. GitHub Agentic Workflows run in GitHub Actions and support GHE Cloud. For data residency configurations, see the [GHE debugging guide](https://github.github.com/gh-aw/troubleshooting/debug-ghe/).

**Q: Can this scale to 100+ repos?**
A: Yes. The agent uses paginated API calls and is instructed to handle rate limits gracefully. For very large orgs, consider filtering `allowed-repos` to active repos or using the `actions` toolset to check for recent workflow runs.

**Q: Can it write to repos it reports on (e.g., create issues in other repos)?**
A: Yes, using `target-repo` in safe outputs. This demo reports only to the digest repo, but you can configure it to create tracking issues across repos. See [Cross-Repository Safe Outputs](https://github.github.com/gh-aw/reference/cross-repository/#cross-repository-safe-outputs).

**Q: What does it cost?**
A: GitHub Actions runner minutes (standard pricing) + AI engine costs (Copilot included with Copilot subscription, or API costs for Claude/Codex). A typical digest run takes 2-5 minutes.

**Q: Can I run this at the org level instead of a user account?**
A: Absolutely. Create the repo under your org (e.g., `my-org/org-weekly-digest`), set `allowed-repos: ["my-org/*"]`, and configure the PAT/GitHub App at the org level.

**Q: What if the agent hallucinates or produces a bad report?**
A: Safe Outputs enforce field-level validation (max title length, sanitized body, max 1 issue per run). The threat detection step catches malicious or nonsensical output. Previous digests are auto-closed, so a bad report is easily identified and replaced on the next run.
